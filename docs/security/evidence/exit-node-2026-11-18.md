# A Tailscale exit node as seen from the routing table, 2026-11-18

A manual run on a Mac (macOS, Tailscale 1.104.6) on a tailnet with exit nodes
of its owner's and no Mullvad add-on on that Mac. It checks the two things
[exit-node recognition](../../peer-gateways.md#mullvad-and-other-tailscale-exit-nodes)
rests on, first with ordinary tools and then with the wallet's code: that the
routing table shows an exit node without anything being sent, and that a
connection bound to the tailnet address cannot leave directly. No wallet was
involved.

The probe, run three times: before, with `tailscale set --exit-node=<a Linux
exit node of the tailnet>`, and after `tailscale set --exit-node=`.

- A datagram socket is connected to `1.1.1.1:53`, to `100.100.100.100:53` and
  to `[2606:4700:4700::1111]:53`, and its local address read (`getsockname`).
  Connecting a datagram socket picks a route and sends nothing.
- A TCP socket is bound to the Mac's tailnet IPv4 address and connected to
  `1.1.1.1:443`, six seconds allowed.
- `https://am.i.mullvad.net/json` is fetched and `mullvad_exit_ip` read.

| | Exit node off (before) | Exit node on | Exit node off (after) |
|---|---|---|---|
| Local address toward the public IPv4 address | the LAN's | the tailnet's (100.64.0.0/10), the same as toward 100.100.100.100 | the LAN's |
| Local address toward 100.100.100.100 | the tailnet's | the tailnet's | the tailnet's |
| Local address toward the public IPv6 address | no route (the LAN has no IPv6) | the tailnet's (`fd7a:115c:a1e0::/48`) | no route |
| TCP bound to the tailnet address, to the public address | timed out after 6.0 s | connected in 0.07 s | timed out after 6.0 s |
| `mullvad_exit_ip` | `false` (the ISP's address) | `false` (the exit node's host) | `false` |

So on macOS the three local addresses tell an exit node from none, and a
connection bound to the tailnet address reaches the internet only through one.
Mullvad's answer had these keys each time: `blacklisted`, `city`, `country`,
`ip`, `latitude`, `longitude`, `mullvad_exit_ip`, `organization`.

## The wallet's own code

Then the same on and off with the wallet's code in place of the probe, at this
change's revision: `tunnelSource`, `detectExitRoute` asking Mullvad through
`curl`, and `PeerConnection.connect` to three public mainnet peers (addresses
from a DNS seed) with the Mac's tailnet address as `tunnel`, each also dialled
unbound as a control. No wallet, no transaction.

| | Exit node off | Exit node on |
|---|---|---|
| `tunnelSource` | none | the tailnet's IPv4 and IPv6 addresses |
| `detectExitRoute` | direct (Mullvad not asked) | an exit node, not confirmed as Mullvad's |
| `TunnelSource.carries` | false | true |
| Three peers, bound to the tailnet address | none reached: each ran into the 8 s deadline | all three answered within 0.5 s (one served compact filters and completed the handshake as `/Satoshi:32.1.0/`; two were refused for not serving them) |
| The same three, unbound | all three answered | all three answered |

Not shown by this run: a Mullvad exit node (`mullvad_exit_ip: true`, and the
server name Winnow shows if Mullvad gives one, were not seen), an iPhone, where
the same kernel routes but Tailscale runs as a different kind of extension, and
a tailnet with IPv6 disabled.
